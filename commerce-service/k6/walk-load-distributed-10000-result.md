### 실행 계획 분석

인덱스가 없는 상태에서 `EXPLAIN`을 통해 실행 계획을 확인한 결과, 전체 테이블을 탐색하는 Full Table Scan이 발생했다.

```sql
EXPLAIN
SELECT *
FROM walk_course
WHERE start_lat BETWEEN 37.559451260933464 AND 37.577469278951476
  AND start_lng BETWEEN 126.96695829336518 AND 126.98969036606668
  AND ST_Distance_Sphere(
      POINT(start_lng, start_lat),
      POINT(126.97832432971593, 37.56846026994247)
  ) <= 1000
LIMIT 3;
```

실행 계획에서 예상 탐색 행이 약 `9,792개`로 나타나 대부분의 데이터를 확인해야 하는 상황임을 확인했다.

### 결과 분석

10,000개 코스를 서울 전역에 분산한 환경에서도 500 VU 부하가 발생하자 주변 코스 조회 P95가 15.09초까지 증가했다.

특히 Full Table Scan으로 많은 행을 후보로 확인한 뒤 `ST_Distance_Sphere()`를 이용해 실제 거리를 계산하고 정렬하는 구조가 병목으로 판단했다.

따라서 Bounding Box 조건에 사용되는 `start_lat`, `start_lng` 컬럼에 복합 B-Tree 인덱스를 적용하고 동일한 조건에서 성능을 재측정했다.

## 5. 10,000개 코스 분산 환경 — `(start_lat, start_lng)` 복합 인덱스 적용 후

### 인덱스 적용

Bounding Box 조건의 후보 탐색을 개선하기 위해 `start_lat`, `start_lng` 컬럼에 복합 B-Tree 인덱스를 추가했다.

```sql
CREATE INDEX idx_walk_course_lat_lng
ON walk_course (start_lat, start_lng);
```

### 실행 계획 비교

인덱스 적용 전에는 약 `9,792개`의 행을 탐색해야 했지만, 복합 B-Tree 인덱스 적용 후 예상 탐색 행이 약 `675개`로 감소했다.

```text
예상 탐색 행
9,792개 → 675개
```

이를 통해 Bounding Box 조건에서 인덱스를 활용하여 거리 계산 단계로 전달되는 후보 데이터를 크게 줄일 수 있음을 확인했다.

### 결과 분석

10,000개 코스 분산 환경에서 복합 B-Tree 인덱스 적용 후 주변 코스 조회 성능이 크게 개선되었다.

- 평균 응답 시간: `6.01s → 39.68ms`
- P95 응답 시간: `15.09s → 98.6ms`
- P99 응답 시간: `15.49s → 357.45ms`
- 예상 탐색 행: `9,792개 → 675개`

특히 P95 응답 시간이 약 **99.3% 감소**하여 목표 응답 시간인 1초 이내를 만족했다.

이를 통해 위치 기반 조회에서 `ST_Distance_Sphere()` 자체에 인덱스를 적용하는 것이 아니라, **거리 계산 전에 Bounding Box 조건으로 후보를 줄이는 단계에 B-Tree 인덱스를 적용하는 방식**이 현재 조회 구조에서 효과적인 것을 확인했다.

### 테스트 데이터 정리
