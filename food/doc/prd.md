## 2. 서비스 목적

FoodLab은 사용자가 직접 요리를 개발하고, 자신이 개발한 요리에 이름을 붙여 다른 사용자들과 공유하는 온라인 요리 연구소이다.

맛, 영양, 경제성, 조리 편의성 등 다양한 요소를 고려하여 효율적이고 만족도 높은 요리를 개발하는 것을 궁극적인 목표로 한다.

사용자는 다른 사용자의 요리를 직접 재현하고 평가하며, 집단지성을 통해 더 나은 식생활을 연구한다.

기존 레시피 서비스처럼 정형화된 요리법을 제공하는 것에 그치지 않고, 누구나 새로운 요리를 창작하고 공유할 수 있는 문화를 지향한다.

## 3. 핵심 가치

- **창의성:** 누구나 자신만의 요리를 개발하고 이름을 붙인다.
- **효율성:** 적은 비용과 노력으로 높은 만족도를 추구한다.
- **집단지성:** 사용자들의 참여와 평가를 통해 요리의 가치를 검증한다.
- **실용성:** 식재료 구매 정보와 조리법을 제공하여 실제 식생활에 활용할 수 있도록 한다.
- **유희성:** Geek 문화와 블랙유머를 통해 서비스 이용 자체에 재미를 부여한다.

## 5. 핵심 기능

### 5.1. 회원 관리

사용자는 회원가입을 통해 FoodLab의 연구원으로 등록할 수 있다.

- 회원가입
- 로그인 및 로그아웃
- 닉네임 설정
- 회원 정보 조회 및 수정
- 자신이 등록한 요리 조회
- 자신이 작성한 평가 조회

비회원은 요리와 평가 정보를 조회할 수 있으며, 요리 등록 및 평가 기능은 회원에게만 제공한다.

### 5.2. 요리 등록

사용자는 자신이 개발한 요리를 실험 보고서 형태로 등록한다.

**등록 항목**

- 요리 이름
- 요리 이미지
- 요리 소개 및 개발 의도
- 필요한 식재료
- 식재료별 수량 및 단위
- 조리 순서(조리 과정을 위해 카드를 하나씩 추가하는 것임. 카드 하나안에 사진 한장(1:1 비율로 조정) 글 하나)

요리 이름은 사용자가 자유롭게 지정할 수 있다.

예시:

- 프로젝트 프로틴 01호
- 월급 전 생존용 탄수화물 복합체
- 제3세대 참치계란밥
- 궁극의 자취생 연료
- 실험체 X-404

작성자는 자신이 등록한 요리를 수정하거나 삭제할 수 있다.

### 5.3. 식재료 관리

식재료 데이터는 관리자가 사전에 일괄 등록하는 방식이 아니라, 사용자들의 요리 등록 과정에서 자연스럽게 축적되는 방식을 사용한다.

**등록 과정**

1. 사용자가 식재료 이름을 입력한다.
2. 기존에 등록된 식재료를 검색한다.
3. 동일한 식재료가 존재하면 해당 데이터를 사용한다.
4. 존재하지 않으면 새로운 식재료로 등록한다.
5. 해당 요리에서 사용하는 수량과 단위를 입력한다.

**관리 정책**

- 식재료 자동완성 검색
- 식재료 이름 정규화
- 동일 식재료 중복 등록 방지
- 기존 식재료 데이터 재사용
- 요리별 식재료 사용량 및 단위 관리

요리와 식재료의 관계는 다대다 관계로 구성하며, 중간 엔티티를 통해 사용량과 단위를 관리한다.

### 5.4. 요리 탐색

사용자는 다양한 조건을 통해 등록된 요리를 탐색할 수 있다.

- 전체 요리 목록 조회
- 요리 이름 검색
- 식재료 이름 기반 검색
- 여러 식재료를 조합한 요리 검색
- 최신 등록순 정렬
- 맛 평가순 정렬
- 조리 편의성 평가순 정렬
- 경제성 평가순 정렬
- 종합 효율 지수순 정렬

식재료 기반 검색에서는 사용자가 보유한 재료를 활용하여 만들 수 있는 요리를 탐색할 수 있도록 한다.

필요한 식재료가 부족한 경우 부족한 재료를 안내한다.

### 5.5. 동료 검증 시스템

사용자는 다른 연구원이 등록한 요리를 세 가지 기준으로 평가할 수 있다.

**평가 기준**

- 조리 편의성 (Ease of Preparation)
- 맛 (Taste)
- 경제성 (Affordability)

각 항목은 1점부터 5점까지 평가한다.

모든 평가 항목은 점수가 높을수록 긍정적인 의미를 갖는다.

즉, 조리 편의성은 조리가 쉬울수록, 경제성은 비용 대비 만족도가 높을수록 높은 점수를 부여한다.

### 5.6. 평가 점수 표현

| 점수 | 조리 편의성 | 맛 | 경제성 |
|---|---|---|---|
| 1 | 박사학위 필요 | 생화학 무기 | 국가 예산 필요 |
| 2 | 대학원생 착취 | 생존 식량 | 재정적 출혈 |
| 3 | 표준 실험 | 정상 식품 | 합리적 지출 |
| 4 | 초보 연구원도 가능 | 도파민 과다 분비 | 자본주의의 기적 |
| 5 | 영장류도 가능 | 신의 물질 | 무한동력 기관 |

평가 문구는 서비스의 컨셉에 맞게 지속적으로 개선할 수 있다.

### 5.7. 평가 정책

- 로그인한 사용자만 평가 가능
- 사용자당 요리별 평가 1회
- 자신이 등록한 요리는 평가 불가
- 세 가지 항목 모두 평가 필수
- 기존 평가 수정 및 삭제 가능
- 항목별 평균 점수 제공
- 전체 평가 참여 인원 제공
- 평가가 없는 요리는 검증 대기 상태로 표시

### 5.8. 종합 효율 지수

세 가지 평가 항목의 평균을 기반으로 종합 효율 지수를 산출한다.

종합 효율 지수 = (조리 편의성 평균 + 맛 평균 + 경제성 평균) / 3

초기 버전에서는 모든 항목에 동일한 가중치를 적용한다.

평가 참여 인원을 함께 표시하여 사용자가 평가의 신뢰도를 판단할 수 있도록 한다.

종합 효율 지수는 영양학적 우수성을 의미하지 않으며, 사용자 평가에 기반한 지표로 제공한다.

### 5.9. 물자 조달 시스템

외부 쇼핑 API를 활용하여 요리에 필요한 식재료의 상품 및 가격 정보를 제공한다.

**제공 기능**

- 식재료별 상품 검색
- 상품 가격 조회
- 조회 결과 내 최저가 탐색
- 가격 오름차순 정렬
- 판매처 정보 제공
- 상품 이미지 제공
- 외부 구매 링크 제공
- 가격 조회 시점 표시

**외부 API 후보**

- 쿠팡 파트너스 API
- 기타 이용 가능한 쇼핑 검색 API
- KAMIS Open API — 농수축산물 가격 참고용

외부 API는 이용 권한, 제공 데이터, 호출 제한 및 이용약관을 검토한 후 확정한다.

검색 결과 내 최저가를 제공하며, 전체 온라인 시장의 최저가를 보장하지 않는다.

상품의 판매 단위, 중량, 배송비 등의 차이를 고려하여 상품 판매 가격과 실제 요리 원가는 구분한다.

FoodLab 내부에서 결제 기능은 제공하지 않는다.

## 8. 시스템 아키텍처

프론트엔드와 백엔드를 분리하여 개발한다.

- React는 사용자 인터페이스 및 클라이언트 상태 관리를 담당한다.
- Spring Boot는 비즈니스 로직, 인증, 데이터 관리 및 외부 API 연동을 담당한다.
- MySQL은 회원, 요리, 식재료, 조리법 및 평가 데이터를 저장한다.
- 외부 쇼핑 API는 식재료 상품 및 가격 정보를 제공한다.
- 이미지 저장 방식은 별도로 설계한다.

프론트엔드는 백엔드 REST API를 통해 데이터를 요청하며, 데이터베이스에 직접 접근하지 않는다.

외부 API의 인증 정보는 백엔드에서 관리하고 프론트엔드에 노출하지 않는다.

- 조리 프로토콜 작성
- 요리 검색 및 정렬
- 식재료 조합 기반 검색
- 세 가지 평가 지표
- 종합 효율 지수
- 외부 API 기반 식재료 상품 및 가격 검색

- 실제 웹서비스 배포

## 13. 향후 확장 기능

MVP 완성 이후 서비스 목적에 부합하는 기능을 단계적으로 추가한다.

### 영양 정보 분석

식품 영양성분 API를 활용하여 식재료 사용량에 따른 영양성분을 계산한다.

- 총열량
- 탄수화물
- 단백질
- 지방
- 나트륨

### 식재료 원가 분석

- 식재료 단위당 가격 계산
- 요리 전체 예상 원가
- 단백질 대비 비용 분석
- 열량 대비 비용 분석

### 파생 요리 시스템

다른 연구원이 등록한 요리를 기반으로 새로운 조리법을 개발할 수 있도록 한다.

오픈소스 프로젝트의 Fork 개념을 요리 개발에 적용한다.

- 원본 요리 참조
- 개량된 요리 등록
- 변경된 식재료 및 조리법 기록
- 원본 및 파생 요리 관계 표시

## 14. 프로젝트 개발 목적

FoodLab은 실제 서비스 구현뿐만 아니라 AI 기반 소프트웨어 개발 역량을 확보하는 것을 기술적 목표로 한다.

AI Agent를 활용하여 요구사항 정의부터 설계, 구현, 테스트, 배포까지 소프트웨어 개발 생명주기 전반을 경험한다.

단순히 AI가 생성한 코드를 사용하는 것이 아니라, 개발자가 요구사항과 기술적 제약조건을 정의하고 결과물을 검증하는 방식으로 진행한다.

## 15. AI 활용 정책

**AI 담당 영역**

- 요구사항 분석
- 시스템 설계 초안 작성
- 데이터베이스 설계
- API 설계
- 백엔드 코드 작성
- 프론트엔드 코드 작성
- 테스트 코드 작성
- 오류 분석
- 코드 리뷰 및 리팩토링
- 기술 문서 작성

**개발자 담당 영역**

- 서비스 방향 결정
- 요구사항 및 개발 범위 통제
- 기술 스택 선택
- 설계 결과 검토
- 생성 코드 검증
- 보안 및 성능 검토
- 테스트 결과 확인
- 최종 구현 승인

**AI 활용 기록**

- 작업별 요구사항 및 프롬프트
- AI가 제안한 설계
- 발생한 구현 오류
- 잘못된 기술적 판단 사례
- 개발자의 수정 및 개선 과정
- 작업별 소요 시간
- 생산성 개선 효과

## 16. 프로젝트 완료 기준

- MVP 핵심 기능이 정상적으로 동작할 것
- 백엔드 REST API 명세가 작성되어 있을 것
- 핵심 비즈니스 로직에 대한 테스트가 존재할 것
- React와 Spring Boot가 정상적으로 연동될 것
- 외부 API 장애가 핵심 서비스에 영향을 주지 않을 것
- 서비스의 디자인 및 브랜드 컨셉이 일관되게 유지될 것
- 외부 사용자가 배포된 서비스에 접근할 수 있을 것
- 개발자가 전체 시스템의 구조와 핵심 비즈니스 로직을 설명할 수 있을 것
- AI 활용 과정과 결과를 기술적으로 설명할 수 있을 것
